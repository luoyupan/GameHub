## 1. 项目概览

GameHub 是一个**完全离线优先**的本地游戏库管理器，把散落在 Steam / Epic / 注册表 / 自定义目录里的游戏汇成一个统一的 Steam 风格封面墙。

### 设计原则

| 原则        | 具体体现                               |
| --------- | ---------------------------------- |
| **只读不写**  | 读取各平台本地数据时严格只读，从不写回任何平台文件          |
| **隐私硬约束** | 绝不读取、更不保存任何平台的密码 / 令牌 / 登录凭证       |
| **离线可用**  | 断网时扫描、启动、分类、统计全部正常；联网只用于封面增强       |
| **不破坏宿主** | Steam 游戏交给 Steam 卸载；删除一律走回收站，绝不永久删 |
| **数据自包含** | 所有数据（含背景图副本）存在同一数据目录，可直接搬走         |

### 技术栈

- 运行时：Electron 33.4.11（Node 22 + Chromium 130）
- 渲染层：**零框架**，原生 HTML / CSS / JavaScript
- 打包：electron-builder 25（Windows portable 单文件 exe）
- 加密：Node `crypto`（scrypt）+ Electron `safeStorage`（Windows DPAPI）

## 3. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                      主进程 (main.js)                     │
│  窗口管理 · IPC 注册 · 后台任务（体积队列 / 巡检 / 自动上锁） │
├─────────────────────────────────────────────────────────┤
│  业务模块层（纯 Node，可单测，不依赖 Electron）             │
│  store · library · scanner · classify · cover · launcher  │
│  platforms · epicauth · mods · stats · uninstall          │
│  appinfo · vdfbin · imgmeta                              │
├─────────────────────────────────────────────────────────┤
│              preload.js（contextBridge 白名单）            │
├─────────────────────────────────────────────────────────┤
│                       渲染进程                            │
│  api.js → state.js → app.js → cards/detail/modals/...    │
│  background.js（外观） · css/（主题与材质）                │
└─────────────────────────────────────────────────────────┘
```

**分层约束：**

- 渲染进程拿不到任何 Node 能力，只能通过 `preload.js` 白名单里的通道
- 业务模块（`scanner` / `classify` / `stats` 等）刻意写成不依赖 Electron 的纯模块，可被 Node 直接单测
- 主进程是**状态权威**：例如「透出桌面」的最终值由主进程换算后推送给渲染层，页面不自己猜

## 5. 主进程模块详解

### 5.1 store.js —— 数据持久化

- 文件：`%APPDATA%\GameHub\library.json`，封面缓存 `covers/`，背景图 `bg/`
- **原子写入**：先写 `.tmp` 再 `rename`，避免断电 / 崩溃写坏存档
- **延迟写盘**：`saveSoon(800ms)` 把高频操作（如更新游玩时长）合并成一次 IO
- **向前兼容**：读档时 `deepMerge(默认值, 读到的数据)`，新增字段自动补到老数据上
- **损坏保护**：JSON 解析失败时先备份成 `library.json.bak` 再用默认值重建

### 5.2 scanner.js —— 游戏嗅探

四条嗅探路径：

| 方法               | 覆盖范围    | 特点                                            |
| ---------------- | ------- | --------------------------------------------- |
| `scanRegistry()` | 注册表卸载项  | 覆盖 90% 已安装游戏，带安装日期                            |
| `scanSteam()`    | Steam 库 | 解析 `libraryfolders.vdf` + `appmanifest_*.acf` |
| `scanEpic()`     | Epic 清单 | 解析 `ProgramData` 下的 `.item` JSON              |
| `scanFolder()`   | 用户指定目录  | 递归 + 启发式识别                                    |

**误报控制**是这里最难的部分：

- **exe 名归一化**：`PotPlayer64.exe` 的 base 是 `potplayer64`，与黑名单 `potplayer` 精确匹配不上。必须先剥掉 `_util` / `_x64` / 数字 / 版本号后缀再比对（同类漏网的还有 `cloudmusic_util`、`TIM3.0`）
- **平台客户端根识别**：不能只看 `steam.exe` 存在（Mod 目录也带），要看「主程序 + 辅助进程同时存在」或强特征文件名
- **分级清理**：手动添加 / 玩过 / 收藏 / 有备注的条目**永远不自动删**

### 5.3 classify.js —— 分类与识别

- `classify(name)`：**25 个分类**，加权关键词匹配，中英文双语词表
- `scoreRegistryEntry()`：给一条注册表卸载项打分，判断「它像不像游戏」
- `pickMainExe()`：从一个目录里挑出最像「游戏主程序」的 exe

用户手动改过的分类会被**锁定**，不被自动归类覆盖。

### 5.4 cover.js —— 封面管理

四种来源，优先级由用户自选：

1. **从 exe 提取图标**（默认，离线可用，square 图标居中贴到渐变底上）
2. **用户手动指定图片**（拖拽 / 文件选择）
3. **联网搜索**：按名字去 Steam 查 AppID，再抓官方封面（搜不到就跳过，不打扰用户）
4. **主题色首字母占位**

`coverKind` 取值：`none` | `icon` | `custom` | `steam`。用户自己设的（`custom`）永远不被自动覆盖。

### 5.5 launcher.js —— 启动与进程守护

- 直接跑 exe / 走 `steam://run/<appid>` 协议 / 走自定义启动参数
- **进程守护计时**：游戏开着时每秒计时，关掉后把时长写回游戏库
- 启动失败给出人话错误（文件不存在 / 权限不足 / 需要管理员）

### 5.6 platforms.js —— 平台数据抓取

**隐私硬约束（改代码时不要破坏）：**

1. 本模块**只读**本地文件，从不写回任何平台的文件
2. 绝不读取、更不会保存任何密码 / 令牌 / 登录凭证
3. 只使用平台客户端已经落在本地的那份数据

### 5.7 epicauth.js —— Epic 登录

让用户在 GameHub 里登录 Epic，读到两样东西：

- 拥有的游戏全清单（**含领了但没下载的** —— 本地清单读不到这些）
- 官方封面图（CDN 直链）

**边界与事实**：Epic **没有**开放面向第三方的玩家数据 API（官方论坛已明确回复）。所以：

- ✅ 能拿到：账号信息、已购游戏清单、官方封面
- ❌ 拿不到：玩家累计游玩时长、成就进度

登录 token 存在 `userData/epic-auth.json`，用 Electron `safeStorage` 加密（Windows 上走 DPAPI，密钥绑当前用户账户）。

> **关于客户端凭据**：源码里的 `CLIENT_ID` / `CLIENT_SECRET` 是 Epic **启动器本体**的公开客户端标识（开源社区 Heroic / Legendary 等普遍这样用），不是任何人的账号密码。不需要改代码即可覆盖：
>
> ```bash
> GAMEHUB_EPIC_CLIENT_ID=xxx GAMEHUB_EPIC_CLIENT_SECRET=yyy npm start
> ```

### 5.8 其它模块

| 模块             | 职责                                            |
| -------------- | --------------------------------------------- |
| `appinfo.js`   | 解析 Steam `appinfo.vdf`，给「没安装的游戏」名字兜底（最准的来源）   |
| `vdfbin.js`    | Binary KeyValues 解析器，读 Steam 成就解锁位图与成就定义      |
| `imgmeta.js`   | 只读文件头几十字节判断图片尺寸，应对 Steam 千奇百怪的封面文件名           |
| `mods.js`      | MOD 管理：Steam 创意工坊（订阅式）+ 本地 MOD，支持启用 / 禁用 / 删除 |
| `stats.js`     | 把游玩流水按 本周 / 本月 / 本季 / 今年 / 全部 汇总              |
| `uninstall.js` | 见 [第 11 节](#11-卸载游戏)                          |

## 7. IPC 通信与 API 分层

```
渲染层  window.API.xxx()
   ↓
api.js  （统一 try/catch + JSON 化）
   ↓
preload.js  contextBridge 白名单
   ↓
main.js  ipcMain.handle(...)
   ↓
业务模块
```

共 **60 个 IPC 通道**，按域分组：

| 域                     | 通道                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------ |
| 应用 / 窗口               | `app:info`、`win:*`                                                                                     |
| 设置                    | `settings:get`、`settings:set`                                                                          |
| 外观                    | `appearance:urls` / `setImage` / `clearImage` / `fonts` / `desktopMaterial` / `desktopMaterialSupport` |
| 游戏库                   | `library:list` / `add` / `addMany` / `update` / `remove` / `clear`                                     |
| 游戏                    | `game:launch` / `stop` / `openFolder` / `calcSize` / `uninstall` / `uninstallInfo`                     |
| 扫描                    | `scan:auto` / `scan:folder` / `scan:cancel` / `scan:defaultFolders`                                    |
| 封面                    | `cover:*`（extract / fetchSteam / searchOne / reset / …）                                                |
| 平台                    | `platform:list` / `sync` / `action`、`epic:login` / `logout` / `status`                                 |
| MOD                   | `mod:list` / `setEnabled` / `remove` / `addManual` / `openWorkshop` / `openNexus`                      |
| 隐藏空间                  | `hidden:setup` / `unlock` / `lock` / `status` / `setHidden` / `changePassword` / `disable`             |
| 统计 / 分类 / 对话框 / Shell | `stats:get`、`category:*`、`dialog:*`、`shell:*`                                                          |

### 反向推送

主进程 → 渲染层的推送只有一个：`appearance:material`（窗口材质变化）。
  
主进程是权威，页面订阅后更新样式，避免两边状态对不上。

## 8. 数据模型与持久化

### library.json 顶层结构

```jsonc
{
  "version": 2,
  "games":    [ /* Game 对象数组 */ ],
  "sessions": [ /* 游玩流水 */ ],
  "settings": { /* 见下 */ }
}
```

### Game 对象主要字段

```js
{
  id, name, exePath, installDir, source,       // 来源：steam / epic / manual / …
  publisher, version, categories: [], altNames: [],
  installDate, sizeBytes, sizeComputedAt,
  favorite: false, hidden: false,
  clearState: 'cleared' | 'multi' | 'uncleared',  // 默认 'uncleared'
  playCount, totalPlayMs, lastPlayedAt,
  playtimeFromSteam: false, steamSyncedAt,     // 时长是否已与 Steam 对过
  coverPath, coverKind, steamAppId, launchArgs, note,
  missing: false, addedAt, updatedAt
}
```


> **不存在「未标记」这一档通关状态**：所有添加的游戏默认未通关，老数据里读到空串一律归到 `uncleared`。

### 设置项（关键部分）

```js
{
  theme: 'dark', sortBy: 'added', viewMode: 'grid', cardSize: 'medium',
  fontFamily: '', fontSize: 13.5,     // 界面字体
  desktopMaterial: 'auto',            // 透出桌面：auto | off | acrylic | mica | tabbed
  bg: {
    sidebar: { type, image, fit, opacity, blur, dim, material, tint },
    content: { /* 同构，两栏独立 */ }
  },
  hidden: { enabled, salt, hash, hint, autoLockMinutes },
  windowBounds: null
}
```

## 9. 外观自定义系统

### 9.1 为什么背景画在伪元素上

背景**不画在元素自己的 `background` 上**，而是画在 `::before`（图片层）和 `::after`（压暗遮罩）两个伪元素上。

好处：内容层的层级、图标的点击区域完全不受影响，也不会出现「改了背景色，结果按钮 hover 底变色」这类连锁反应。

### 9.2 层叠：沉背景而不是抬内容

```css
.sidebar, .content { position: relative; isolation: isolate; }
.sidebar::before, .content::before,
.sidebar::after,  .content::after { z-index: -1; }
```

> ⚠️ **血的教训**：最初写的是 `.content > * { z-index: 1 }`（抬内容），结果顶栏的「⋮ 更多选项」下拉菜单被下面 DOM 靠后的卡片区盖住了。
>
> **「抬内容」和「沉背景」效果看似一样，但抬内容会改变层叠上下文，把原本能浮起来的东西（下拉、tooltip）一起压住。**
>
> `isolation: isolate` 把负 z-index 关在本容器内，伪元素落在「容器背景之上、内容之下」，正好是想要的层次。

### 9.3 四种材质

| 材质             | 不透明度（常规） | 不透明度（透视版） | 观感                        |
| -------------- | -------- | --------- | ------------------------- |
| 磨砂玻璃 `frosted` | 0.86     | 0.30      | 强模糊 + 轻微降饱和，隔一层毛玻璃        |
| 亚克力 `acrylic`  | 0.78     | 0.22      | 中等模糊 + 提饱和提亮，接近 Win11 亚克力 |
| 玻璃 `glass`     | 0.66     | 0.16      | 轻模糊 + 明显厚度与高光边            |
| 液态玻璃 `liquid`  | 0.62     | 0.13      | 有体积感，见下                   |

**共同约束：必须有实体感。** 纯半透明叠深色底会看起来像个「透明窟窿」，所以每种材质都给了：一层底色 + 一层纵向高光 + 内嵌高光边。

**液态玻璃**的「体积感」靠四层光叠出来：

- 顶部一条 2px 的窄亮边（玻璃边缘折射高光 —— 这是「液态」最关键的一笔）
- 左上角柔和的镜面高光
- 右下角冷色反射 + 左下角暖色微光（制造液体的色温差）
- 底部内阴影压出厚度 + 外投影让它从背景上浮起来

```css
backdrop-filter: blur(27px) saturate(205%) brightness(1.16) contrast(1.03);
```

### 9.4 氛围光

`backdrop-filter` 需要有「背后有东西」才看得出来。启用材质时给 `.app` 加 `.has-material` 铺一层氛围渐变光（左上偏蓝、右下偏青、中间一点紫）。

alpha 要够浓（0.46 / 0.38 / 0.26）—— 第一版用 0.22 完全看不出效果。

同步逻辑用 `syncAmbientFromDom()`：**直接看 DOM 上挂着哪个类**，而不是读设置对象 —— 因为设置面板改材质走的是 `applySlot`（实时预览），读设置会漏。

### 9.5 字体与字号

- 字体列表：`reg query` 读注册表拿全量，失败回退**内置 60+ 精选预设**
  > 实测部分环境 `reg.exe` 被安全策略黑名单拦掉 —— 所以预设表必须够全，并支持用户**手输字体名**，两条路都要有
- 字号全局生效：`tools/rewrite-font-size.py` 把 CSS 里 **182 处**正文级字号（10~15px）批量改成 `calc(var(--fs-base) * 系数)`，系数 = 原值 / 13.5，所以默认值下渲染结果与改动前完全一致（实测 `.si-label` 13.0005px vs 原 13px）。18px+ 的大标题保持固定，避免撑坏版式。

## 10. 透出桌面（窗口材质）

### 10.1 核心事实

> **CSS `backdrop-filter` 只能采样「页面内」已画出的内容，永远看不到桌面。**

无论把材质层调得多透，底下也只有深色的页面底色。想让窗口真的透出桌面，只能让 Windows 的 DWM 去合成 —— 也就是主进程的 `win.setBackgroundMaterial()`。

### 10.2 实现：材质 ↔ 透出桌面 自动联动

`desktopMaterial` 取值：`auto`（默认）/ `off` / `acrylic` / `mica` / `tabbed`

```
auto → 左右任一栏用了玻璃系材质（frosted/acrylic/glass/liquid）
       → 窗口自动开 acrylic
       → 换回图片或纯色底 → 自动收回
```

- **主进程是权威**：`resolveDesktopMaterial()` 换算后经 `appearance:material` 推送给渲染层；渲染层首屏用同一套规则镜像计算，之后以推送为准
- 旧数据里的 `'none'` 兼容为 `auto`（否则老用户开了玻璃材质也透不出桌面）
- 系统要求：Windows 11（build ≥ 22000），其它系统静默忽略

### 10.3 透视版材质变量

开了透出桌面后，CSS 把 `--mat-*` 换成 `--mat-*-see`：

```css
html[data-desktop-material] {
  --mat-frosted: var(--mat-frosted-see);
  --mat-acrylic: var(--mat-acrylic-see);
  --mat-glass:   var(--mat-glass-see);
  --mat-liquid:  var(--mat-liquid-see);
}
```

**只降底色不降高光** —— 折射高光 / 镜面光 / 内嵌边是「玻璃感」的来源，留着它们，面板放透之后依然像一块玻璃，而不是一块空缺。

液态玻璃放透后去掉外投影（黑影会糊在桌面上），内嵌高光与底部内阴影保留。

## 11. 卸载游戏

三类游戏的卸载方式完全不同，`src/main/uninstall.js` 分开处理：

| 类型          | 方式                                                                | 理由                                                                           |
| ----------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Steam**   | `steam://uninstall/<appid>`                                       | Steam 有自己的库状态、清单、云存档。我们直接删目录会让它变成「文件缺失」坏状态                                   |

### 安全红线（写死在代码里）

- **禁删系统目录**：盘符根 / Windows / Program Files 根 / 用户目录根
- **删除一律走回收站**
- 每次卸载前把「要删什么」报清楚

### 库记录何时清

只有 `remove`（用户就是要清）和 `trash`（文件已进回收站）才顺手删记录；
  
`platform` 和跑卸载向导的情况**先留着** —— 那些流程还没走完，删了记录用户就找不回条目了。

## 13. 内置浏览器与 MOD 下载

### 13.1 这个功能要解决什么

在 MOD 这件事上，最容易踩的坑不是下载不下来，而是**放错目录** ——
  
而且放错**不会报错，只会静默失效**：进游戏一看，MOD 没生效，日志里什么都没有。

原本「N 网找 MOD」是丢给系统浏览器的：文件落到「下载」目录，
  
用户得自己找文件、自己解压、自己判断该放哪个游戏的哪个子目录。
  
内置浏览器把这个链路整个接过来：在软件内打开 N 网 → 下载被接管 →
  
按规则直接落到这款游戏的 MOD 目录 → 按需自动解压。

顺带一个附加好处：N 网给免费用户的「断点续传」在 Chromium 内核下支持最好，
  
而 Electron 就是 Chromium。

> **形态变更史**（三版，每一版都是用户反馈直接推动的）：
>
> | 版本           | 形态                           | 被否掉的原因                            |
> | ------------ | ---------------------------- | --------------------------------- |
> | v1（1.1.0）    | 独立弹窗（自绘工具条的 `BrowserWindow`） | 「不要额外弹窗」                          |
> | v2（1.1.1）    | 主界面顶部导航栏标签页                  | 「不要跳转出去，太突兀了」—— 一点 N 网整个内容区被浏览器顶掉 |
> | v3（1.1.2，当前） | **内嵌在 MOD 管理面板里**，只占那一块区域    | —                                 |
>
> v3 的落点是：MOD 管理卡片上多一个「🌐 N 网」按钮，点了就在**该游戏的 MOD
>   
> 面板内部**展开浏览器，游戏列表、其它卡片都还在原位。再点一次「🌐 收起 N 网」收起。
>
> 三版能低成本换来换去，是因为 **webview 的宿主容器被抽成了 `createPane()`**，
>   
> v2/v3 只是往不同父节点里塞同一个 pane，下载接管那套一行没动。

### 13.2 模块构成

| 文件                               | 职责                                                    |
| -------------------------------- | ----------------------------------------------------- |
| `src/main/browser.js`            | `BrowserTabsService`：标签注册表 + session 下载接管 + 事件出口      |
| `src/main/modpaths.js`           | MOD 目录规则引擎（纯 Node，可单测）                                |
| `src/main/unzip.js`              | 纯 Node ZIP 解压（含 Zip Slip 防护）                          |
| `src/renderer/js/browserview.js` | `createPane()`：webview 容器 + 工具条 + 下载进度 + 错误页；两种挂载形态共用 |
| `src/renderer/js/modview.js`     | MOD 面板：内嵌浏览器的展开/收起（`toggleBrowser`）                   |
| `src/renderer/css/browser.css`   | 内嵌浏览器样式（pane / 工具条 / 错误页 / 下载进度）                      |

主进程与渲染层的分工：**webview 归渲染层管**（创建、显示、导航、事件），
  
主进程只做渲染层做不了的三件事 —— 独立 session、will-download 下载接管、
  
必要时弹系统对话框（「每次问我」模式）。

### 13.3 MOD 目录规则引擎（联网查证后的结论）

规则优先级：**手动指定 > Steam AppID 精确匹配 > 名称关键词 > 目录探测兜底**。
  
另外只要磁盘上真有符合常见命名的目录，就以它为准 ——
  
实测目录比规则推断可靠。

一部分规则是**反直觉**的，也是这套引擎存在的意义：

| 赛博朋克 2077          | `archive/pc/mod`                                     |                      |
| 艾尔登法环              | `Game/mod`                                           |                      |

| 我的世界               | `%APPDATA%\.minecraft\mods`                          | 同上                   |

**认不出来时不硬猜**：退化成弹窗让用户选一次。
  
理由就是开头那句 —— 放错不报错，比让用户多点一下糟得多。

### 13.4 下载落点决策（`main.js` 的 `decideModDownloadDir`）

三种模式（设置里选）：

| 模式               | 行为               |
| ---------------- | ---------------- |
| 自动进游戏 MOD 目录（默认） | 按 13.3 的规则推断     |
| 固定文件夹            | 一律落到设置里指定的目录     |
| 每次问我             | 弹保存对话框，默认位置填推断结果 |

界面预览（`mod:downloadTarget`）和下载回调**共用同一份函数**，
  
避免"界面显示 A、实际存到 B"这种最难查的不一致。

### 13.5 创意工坊跳转：走 Steam 客户端，不跳浏览器（v1.3.2）

**主人的要求**：点创意工坊要进 **Steam 软件**，不要开外部浏览器。

原因很实在 —— **订阅 / 退订 / 自动下载这些动作只有 Steam 客户端能做**。
网页版只能"看"，点订阅最后还是要把你弹回客户端，等于让人白绕一圈。

| 入口 | 走哪 |
|---|---|
| 「➕ 添加 MOD」（Steam 游戏） | **`steam://url/SteamWorkshopPage/<appid>`** → Steam 客户端 |
| 空列表里的「🛠 去创意工坊看看」 | 同上（Steam 客户端） |
| 「🌐 网页版」 | `https://steamcommunity.com/app/<appid>/workshop/`（浏览器，只作补充） |

**⚠ 一个必须绕开的坑**：`shell.openExternal('steam://…')` 在**没装 Steam** 的机器上
**不会抛错** —— Windows 只会弹一个"你要用什么程序打开它"的系统框，
用户点了半天没反应，而 `try/catch` 完全抓不到。

所以不能靠异常判断成败，得**主动先查一遍 Steam 装没装**：

```js
const steamDir = await platforms._internals.Steam.findInstall();
if (!steamDir) → 直接开网页版，并返回 fellBack:true（界面如实提示"没检测到 Steam 客户端"）
```

`findInstall()` 复用的是 scanner 那套成熟逻辑（探盘符 + 读 `libraryfolders.vdf`），
认得出 `I:\Steam` 这种非常规位置。

> 万一哪天 `SteamWorkshopPage` 这个 protocol 失效了，备选是
> `steam://openurl/` + 网页地址 —— 同样是在 Steam 里开，只是走内置浏览器。

### 13.6 预留的扩展接口

需求明确要求「预留接口方便后续修改及添加功能」，
  
所以服务把「标签显示」和「下载接管」分开，上层只依赖这几个口子：

主进程 `BrowserTabsService`：

| 接口                                              | 用途                                                         |
| ----------------------------------------------- | ---------------------------------------------------------- |
| `open(url, { title, context })`                 | 登记一个标签，`context` 会原样带回给下载回调                                |
| `attach(tabId, wcId)`                           | 渲染层登记 webview 的 guest id（下载归属反查用）                          |
| `navigate(tabId, url)` / `update(tabId, patch)` | 跳转 / 记账                                                    |
| `close(tabId)` / `list()` / `destroy()`         | 生命周期                                                       |
| `onDownload(info)`                              | 问主进程「存哪」，支持返回 Promise —— 换落点策略只改这一个回调                      |
| `onEvent(ev)`                                   | 统一事件出口（tab-opened / navigated / download / download-done…） |

渲染层 `window.BrowserTabs`：

| 接口                                          | 用途                                           |
| ------------------------------------------- | -------------------------------------------- |
| `modElement(game)`                          | 造一个挂在 MOD 面板里的 pane（**v3 主入口**，modview.js 用） |
| `modResume()` / `modOpen(g)` / `modClose()` | 恢复上次地址 / 打开 / 收起并销毁                          |
| `open({ url, title, context, target })`     | 开一个导航栏标签（v2 形态，保留备用）                         |
| `activate(id)` / `close(id)` / `hideAll()`  | 激活 / 关闭 / 切回游戏库时收起                           |

`createPane(container, opts)` 是形态无关的：传什么容器它就长在哪，
  
内部自己管 webview 生命周期、工具条、下载进度、加载失败错误页。
  
以后要再换形态（左右分屏、独立窗口、多开），
  
**只是换 `createPane` 的父节点**，下载落点那套一行不用动。

配套的 IPC：`mod:browse` 现在返回 `{ tabId, url, target }`（v1 只回一个 url），
  
`browser:closeTab` 让渲染层能主动注销标签，避免切游戏后留下僵尸标签。

### 13.7 安全边界

浏览器标签里跑的是**外部不可信站点**，所以：

- `<webview>` **不写** `nodeintegration` 属性，只在 `webpreferences` 里给
    
  `contextIsolation=true`
    
  ⚠ 早期版本写过 `nodeintegration="false"`，这是**错的** ——
    
  它是布尔属性，**只要出现在标签上就是启用**（不看值），
    
  等于给 N 网页面开了 Node 能力。必须整个属性不写。
- guest 跑在独立进程里，**拿不到**宿主页的 preload 和任何 Node 能力
- 独立 session 分区 `persist:gamehub-browser`，不污染主界面登录态
- 只放行 `http(s)`；`nxm://` 之类协议交给系统处理
- 解压有 Zip Slip 防护（拒绝绝对路径、`..` 越界）
- 主页面 CSP 补了 `frame-src https: http:`，否则 webview 加载远程页面会被拦

### 13.8 踩过的坑（本功能专属）

- **`WebContents` 的 id 是属性 `wc.id`，没有 `getId()` 方法** ——
    
  调 `wc.getId()` 抛 TypeError，被 try 吞掉后下载归属永远查不到，
    
  表现是「下载被莫名其妙取消」。这是本功能排查最久的一个。
- **`<webview>` 不写 `partition` 就整个失效**：
    
  不指定分区时 webview 跑在默认 session 上，
    
  主进程挂在 `persist:gamehub-browser` 上的 `will-download` **永远收不到**，
    
  表现是"下载了但没接管"。
- **白屏是三个原因叠出来的**，只修一个都不够（实测排查顺序即优先级）：
  1. **主窗口没开 `webviewTag: true`**（主因）—— 不开这个，`<webview>` 标签
       
     整个是死的，用户看到的就是 pane 的白色底色。**这个不修，后面两条修了也没用。**
  2. **`src` 在 append 之前设** —— webview 还没进 DOM 时设的初始导航会被丢弃，
       
     永远停在 `about:blank`。必须 `stage.appendChild(wv)` 之后再 `setTarget/navigate`。
  3. **页面 CSP 的 `default-src 'self'`** 会拦掉 webview 里的远程页面，
       
     要补 `frame-src https: http:`。
       
     另外 `did-fail-load` 要**跳过 errorCode -3**（用户主动中止，不是错误），
       
     否则点个链接就弹错误页。
- **下载来自 guest webContents**，不等于宿主窗口的 `webContents`，
    
  直接 `===` 比对全部失配。要在 webview `did-attach` 时把
    
  `getWebContentsId()` 报给主进程登记（`browser:attach`）。
- **`setSavePath` 必须给完整文件路径**，只给目录会静默走默认下载路径。
- **上层没配 `onDownload` 时不能顺手取消下载** —— 无声无息消失比存错地方更难查。
- 本机调试若 GPU 进程 FATAL，加 `--no-sandbox` 可绕过（沙箱拉不起 GPU 进程）。

### 13.9 Cloudflare 人机验证：为什么内嵌浏览器过不去

现象：N 网点开卡在「请稍候… / Just a moment…」，转圈不放行。

**先说结论：伪装解决不了，得留一条确定的出路。** 排查过程与实测数据都在
  
`tools/dev/cf-probe.js`（真机读一遍浏览器指纹，判定是否被 challenge），
  
下次再遇到直接跑它，不要靠猜。

**根因是「UA 与 Client Hints 不自洽」**：

```
navigator.userAgentData.brands = [ {Not?A_Brand,99}, {Chromium,130} ]  ← 缺 Google Chrome
User-Agent: ... Chrome/130.0.6723.191 ...                              ← 却自称 Chrome
```

UA 清洗（13.7 那条）去掉了 Electron 尾巴，但 Client Hints 还是 Electron 自己的 ——
  
「自称 Chrome 却不带 Google Chrome 品牌」正是 Cloudflare 判定伪装/自动化的强特征。

已做的两层修正（版本号统一取 `process.versions.chrome`）：

| 层     | 做法                                                                       | 为什么必须这么做                                         |
| ----- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| 请求头   | `session.webRequest.onBeforeSendHeaders` 补 `sec-ch-ua` 系列                | —                                                |
| 页面 JS | CDP `Page.addScriptToEvaluateOnNewDocument` 覆盖 `navigator.userAgentData` | **preload 跑在隔离世界，改不到页面的 navigator**；且必须在页面脚本之前生效 |


**但实测仍然过不去**（等 60 秒、cookie 为空）—— Cloudflare 对 Electron 的识别
  
不止这一项。所以真正的解法是**把通行证搬过来**：

1. 用户在系统浏览器过验证（自己的 Chrome/Edge 一定能过）
2. F12 → Application → Cookies → 复制 `cf_clearance`
3. 粘进面板的 🛡 输入框 → 主进程 `session.cookies.set()` → 刷新

服务侧接口是 `setCookie(url, raw)`：支持整串 Cookie，会自动剔除
  
`Path/Secure/HttpOnly` 这类控制属性。

> 顺带一个反直觉的实测结果：**WebGL 是可用的**（`ANGLE (Google, Vulkan 1.3.0
> (SwiftShader Device (Subzero)))`）。即便主进程 `disableHardwareAcceleration()`
>   
> 了，Electron 33 仍走 SwiftShader —— 所以"过不去"不要往 GPU 方向找原因。

**实测结论（v1.1.6 之后）：复制 cf_clearance 这条路也走不通，此功能搁置。**

主人实测（Chrome DevTools 里复制了 cf_clearance 粘入）依然过不去 ——
  
和预期中的风险一致：`cf_clearance` 绑定的不只是 IP，还包括**完整浏览器指纹**
  
（UA 只是其中一项）。内嵌浏览器与真实 Chrome 在指纹层面差异太多，
  
Cloudflare 的校验单靠一个 cookie 搬运骗不过。

**现状**：N 网的人机验证在内嵌浏览器里就是过不去，面板里的 🛡 引导保留
  
（万一某些站点指纹要求低），但不要指望它。下载 MOD 的替代路径：
  
系统浏览器下载 →「⬇ 快速导入」拖进来（见 13.9）→ 自动解压落位。
  
此问题留待以后有更好的方案（比如换内核、或 Cloudflare 官方通道）再解。

### 13.10 MOD 快速导入与对齐工具（v1.2.0）

N 网验证过不去 → 下载回到系统浏览器 → 文件躺在「下载」目录 →
  
原来得自己解压、自己找目录。这组功能把"下载之后"的整段链路接回来：

| 功能               | 入口      | 做什么                                              |
| ---------------- | ------- | ------------------------------------------------ |
| ⬇ 快速导入           | MOD 工具行 | 拖 zip / 文件夹进对话框 → 自动解压/复制进该游戏的 MOD 目录            |
| 🧮 对齐 → 📦 快速打包  | 对齐弹窗    | 把这款游戏全部 mod 压成一个 zip（纯 Node 打包器，见下）              |
| 🧮 对齐 → 🔢 MOD 码 | 对齐弹窗    | 按 mod 名称+数量生成 `GHMOD1-<数量>-<crc>-<base64url>` 短码 |
| 🧮 对齐 → 📥 对比    | 对齐弹窗    | 粘别人的码 → 列出「你缺的」「你多的」                             |

**拖放拿路径的坑（Electron ≥32）**：`dataTransfer.files` 里的 File
  
**已经没有 `.path` 属性了**，必须经 preload 里的
  
`webUtils.getPathForFile(file)` 换 —— File 对象过不了普通 IPC，
  
contextBridge 暴露的函数是唯一通道（`API.pathForFile`）。

**zip 打包器是手写的**（`main/zipwrite.js`）：Node 没有原生 zip 打包 API，
  
项目又坚持零依赖。结构就是「本地文件头 × n + 中央目录 + EOCD」，
  
压缩用 `zlib.deflateRawSync`（zip 的 deflate 就是裸 deflate 流），
  
CRC32 查表法自己实现。**产出必须能被自家 unzip.js 原样解回** ——
  
modport-test.js 里有中文名 + 嵌套目录 + store 模式的往返测试盯着。

**MOD 码的两个设计约束**：

1. **必须确定性**：同一份 mod 清单在任何机器上生成的码要一模一样。
     
   所以排序用码点序（`sort()` 默认）而不是 `localeCompare` ——
     
   后者跟着机器 ICU 走，中文排序规则可能不同，码就对不上了。
2. **自校验**：码里带数量 + deflate 后载荷的 CRC32。复制时漏了尾巴、
     
   中间被改一个字符，直接报「码不完整」而不是给你一份错误的对比结果。
     
   （注意：base64 的尾字符可能落在填充位，改它不影响解码字节 ——
     
   测试篡改载荷要改中段。）

对齐的判定规则：**忽略大小写、全角括号归一、多余空格** ——
  
`skyui （中文版）` 和 `SkyUI (中文版)` 算同一个 mod。

## 14. 联机（v1.3.0）

### 14.1 三种模式，各管一种网络处境

顶部导航栏新增「联机」入口。三种模式不是三个平行功能，而是**按"你的网络能不能直连"递进**的：

| 模式       | 谁负责把流量送过去                    | 适用                | GameHub 做什么                      |
| -------- | ---------------------------- | ----------------- | -------------------------------- |
| 🛰 内网穿透  | 你自己在跑的穿透工具（樱花联机 / frp / 花生壳） | 任何网络，最稳           | 把 `域名:端口` 封装成房间码、TCP 连通性测试       |
| ⚡ P2P 直连 | 双方直连（IPv6 或公网 IPv4）          | 有公网 IPv6，或公网 IPv4 | **网络体检** + 建房/加入 + 实时延迟丢包 + 游戏隧道 |
| 🔁 中转站   | 玩家自己提供的服务器                   | 直连不通、又不想折腾穿透      | 连接 + 建房/加入 + 实时延迟丢包 + 游戏隧道       |

每张模式卡上都有一条黄底「**做不到**」说明 —— 这个功能做不到什么必须提前讲清楚，
  
别让人填完表单才发现根本不是这么回事（穿透不是 GameHub 做的；中转站没有官方的）。

### 14.2 网络体检（`main/net/netprobe.js`）

建房之前先回答"你这网络能不能直连"。纯 UDP 出站，不需要部署任何东西：

1. **枚举网卡**（`os.networkInterfaces`），按"能不能被别人直接连到"分三桶：
   - 公网 IPv4：排除 RFC1918（10/8、172.16/12、192.168/16）、**运营商大内网 100.64/10（CGNAT）**、127/8、169.254/16
   - 公网 IPv6：只认全球单播 **2000::/3**（排除 fe80 链路本地、fc00::/7 ULA、::1）
   - 其余归为内网地址
2. **STUN 探测**（RFC 5389 Binding Request，手搓 20 字节）：并行问 4 台公共 STUN
     
   （stun.qq.com / stun.miwifi.com / stun.syncthing.net / stun.l.google.com），谁先答用谁。
     
   映射地址 == 本机网卡地址 → 你就在公网上；否则你在 NAT 后面。
3. **结论三档**：`ipv6-ok`（有公网 IPv6）/ `p2p-ok`（公网 IPv4）/ `limited`（建议换穿透或中转站）。
     
   `limited` 时界面出黄条警告，但**不禁止**建房 —— 万一呢，用户自己决定。

> ⚠ 实测本机环境：NAT 出口 183.219.113.202，结论 `limited` ——
>   
> 这正是大多数家宽的真实处境，所以"中转站/穿透"不是摆设，是主路径。

**一个容易写错的细节**：STUN 探测必须**复用房间的那个 UDP socket**（`stunProbeOnSocket`），
  
不能用新建的 socket 去问。NAT 的端口映射按 (本机IP, 本机端口) 分配，换 socket 就是另一条映射、
  
另一个外网端口，问出来的结果对房间毫无用处。房主先绑好端口、再用同一个 socket 问，拿到的才是
  
"别人真能连进来"的 ip:port。建好房后还要定时（20s）往 STUN 发个包**保活这条映射**，洞才会一直开着。

### 14.3 房间码（`main/net/codecs.js`）

格式 `GHNET1-<crc32hex>-<base64url(deflateRaw(JSON))>`，和 MOD 码同一家族：

- 码里只有：模式 / 房间名 / 地址 / 端口 / 游戏端口 / 有无密码 / 游戏名
- **密码永远不进码**，连密码哈希也不进（防离线爆破）；密码只参与本机算 `rid`
- **CRC 自校验**：复制漏了尾巴、被改了一个字符，直接判"码无效"而不是解析出乱七八糟的东西
- **白名单清洗两次**：生成前洗一次，**从码里解出来还要再洗一次** —— 码是别人给的，不可信；
    
  `host` 只放行 `[a-zA-Z0-9.\-:\[\]]`，塞 URL / 脚本进码会被直接拒
- `rid` = `sha256(房间名::密码::gamehub).slice(0,16)` —— 不知道密码就算拿到码也算不出 rid

### 14.4 房间协议（`main/net/protocol.js` + `main/net/roomsvc.js`）

一条 UDP 通道跑全部：**帧头 12 字节**（magic 'GH' / 版本 / 类型 / seq / to）+ 载荷。

| 类型                  | 方向   | 载荷                        | 用途         |
| ------------------- | ---- | ------------------------- | ---------- |
| HELLO               | 客→服  | `{rid, name, role}`       | 入房申请       |
| WELCOME             | 服→客  | `{id, hostId, members[]}` | 发 id + 成员表 |
| REJECT              | 服→客  | `{reason}`                | rid 对不上    |
| JOIN / LEAVE        | 广播   | `{member}` / `{id}`       | 成员变动       |
| PING / PONG         | 双向   | `{ts, from}`              | 延迟与丢包      |
| STATS               | 房主广播 | `{rows[{id,rtt,loss}]}`   | 全房间质量表     |
| OPEN / CLOSE / DATA | 隧道   | connId(+bytes)            | 游戏流量       |

**延迟与丢包怎么算**：每 1 秒互发一次 PING/PONG。
  
丢包率用**滑动窗口**（最近 30 次心跳）算，只统计**已经出结果**的包 ——
  
回了的不算丢，超过 2.5 秒还没回的算丢，刚发出去还没到点的不参与计算，否则丢包率会虚高。
  
房主每 2 秒广播一次 STATS，所以客人也能看到"别人到房主"的质量。
  
房主侧掉线判定 12 秒；客人侧房主 12 秒没消息 → 判"房主掉线"自动退出。

**为什么要有帧头里的 `to` 字段**：中转站服务器是把包**广播**给同房间其他人的，
  
客户端必须自己认领"发给我的"包；P2P 直连时收发都是点对点，`to` 写 0 即可。
  
但 WELCOME / REJECT 要无条件放行 —— 收到它们时客户端还没被分配 id，帧头的 to 对不上。

### 14.5 游戏隧道（TCP over UDP，实验特性）

很多游戏只支持"局域网联机"。隧道让它跨网也能跑：

```
客人游戏 ──TCP──> 127.0.0.1:本地端口(客人 GameHub)
                    │ 封成 DATA 帧
                    ▼ (UDP)
                房主 GameHub ──TCP──> 127.0.0.1:游戏端口(房主的游戏)
```

- 客人侧起一个本地 TCP 监听；房主侧收到 OPEN 后 `net.connect` 到本机游戏端口，两头泵字节
- connId 用 `crypto.randomInt` 生成（31 位），多人同时连不撞号
- **诚实标注**：TCP 跑在 UDP 上没有重传/拥塞控制，大流量传输性能有限，
    
  局域网类游戏的小包场景通常够用 —— 所以界面写的是"实验特性"

### 14.6 中转站（玩家自备，`tools/relay-server.js`）

**GameHub 不提供任何官方中转站**。玩家自己找台有公网 IP 的机器：

```
node relay-server.js 40000 8      # 端口、每房人数上限
npm run relay                     # 本项目里的快捷方式
```

单文件、零依赖、可直接拷去服务器。它只做一件事：**按 rid 把 UDP 包在同房间的人之间原样广播**。

- 看不懂游戏内容（载荷对它是不透明字节）
- 看不懂房间名/密码（只看到一个 rid 哈希）
- 不落盘、不记录、重启即空

中转站模式下密码的语义有个细节：rid 不对时中转站会给你**新开一个空房间**而不是拒绝
  
（它根本不知道"正确的 rid"是什么）。所以客户端进完房发现屋里一个人都没有时，
  
要**主动判失败**并提示"房间名或密码不对，或者房主已经关了" —— 不能让人对着空房间发呆。

### 14.7 安全与免责（写死在界面里）

- 密码永不上网；房间码不透明且带 CRC
- 中转站地址由玩家自己填，**GameHub 不提供、不为陌生地址与码负责** —— 中转站表单里有红底免责声明
- 从码里解出来的数据一律再过一遍白名单（不可信输入）

### 14.8 两栏布局与房间聊天（v1.3.1）

**布局**（照主人画的草图）：左栏 = 原本的联机操作区；右栏 = 常驻的房间信息区，
  
从上到下是「房间状态（我的延迟/丢包 + 昵称）→ 成员表（**账号 / 延迟 / 丢包** 三列）→ 聊天框」。
  
右栏 `position: sticky` —— 左栏很长，往下滚也看得到自己卡不卡、谁在房间里。

**聊天**：

- 帧类型 `CHAT {text, from, name}`。P2P 模式房主逐个 unicast 给每个成员；
    
  中转站走广播、客户端按 `to` 认领（和 STATS 一个路数）
- **昵称每*条消息都带上，主进程不存****&#x20;—— 改名立刻在聊天里生效，成员表要重进房间才换
    
  （成员表的名字来自 HELLO，房间里没有"改名"这*种帧；不值得为它加协议）
- 昵称存 localStorage：这是本地偏好，不值得动全局设置 schema
- 自己的消息名字是绿色（`nrc-line.me`），和别人的蓝色区分

**每秒刷新的分级**（防焦点丢失，这个坑值得单独记）：

联机页每秒收到一次房间快照。最偷懒的做法是整页重画，但那会把
  
**正打到一半的昵称/聊天输入框清空、焦点踢飞**。所以：

| 变化              | 怎么刷                            |
| --------------- | ------------------------------ |
| 延迟/丢包数字         | 只改 `textContent` + 卡片的颜色 class |
| 成员表             | 整卡重画（里面没有输入框，安全）               |
| 昵称框 / 聊天输入框     | **永远不重画**                      |
| 进房 / 掉线（布局形态变了） | 才整页重画                          |

## 14.9 ⚠ 测试状态坦诚书：联机功能**没有经过真实网络验证**

**这一节请务必读完再判断"这是不是 bug"。**

### 它被测到什么程度

| 被测过的                     | 怎么测的                           |
| ------------------------ | ------------------------------ |
| 房间码编解码 / 白名单 / 防篡改       | 单元测试，79 项                      |
| 地址分类（公网 IPv4、IPv6、CGNAT） | 单元测试                           |
| 报文编解码                    | 单元测试                           |
| 延迟 / 丢包计量                | 单元测试                           |
| 网络体检（STUN 探测）            | **单机**实机跑过 —— 只证明"问得出去、拿得到回应"  |
| 建房 → 握手 → 心跳 → 成员表       | **127.0.0.1 上两个进程**跑通过         |
| 游戏隧道（TCP→UDP→TCP）        | **127.0.0.1 上**跑通过（假游戏服 echo）  |
| 中转站                      | **127.0.0.1 上 spawn 一个真进程**跑通过 |
| UI 全流程                   | 真机探针 0 报错                      |

### 它**没有**被测过什么（重点）

- **没有两台真实机器、跨公网、跨运营商跑过一次**
- **没有在真实的 NAT 环境里验证过打洞成不成功** —— STUN 能问出映射地址，
    
  但"锥形 NAT 能不能被打穿"这件事只有真连一次才知道
- **没有验证过任何一款真实游戏的联机流量** —— 隧道那条链路只跑过 echo 测试
- **没有验证过中转站跑在真实公网服务器上**的表现（丢包、带宽、并发）
- **没有验证过 IPv6 直连**（本机没有公网 IPv6，那一条分支只走过单元测试）

### 所以，遇到这些情况是"正常"的

| 现象              | 最可能的原因                               |
| --------------- | ------------------------------------ |
| 房间码发出去了，朋友连不进来  | 房主在对称型 NAT / 运营商大内网后面，打洞失败 → 换穿透或中转站 |
| 能连上但延迟几百 ms、丢包高 | 中转站绕路，或 UDP 在运营商那里被限速                |
| 开了隧道游戏还是连不上     | 游戏走的是 UDP（隧道目前只转发 TCP），或端口填错了        |
| 成员表里的延迟一直是 0    | 只有两个人时很正常 —— 本机回环就这么快                |
| 中转站连不上          | UDP 端口没放行（云服务器安全组 / 本机防火墙）           |

### 欢迎提 bug

这个项目由 AI 开发（见 README），**联机是本仓库里最依赖真实网络环境、也最难在开发环境里
  
自证的一块**。如果你在实际使用中遇到问题：

- 把**联机页最下面的日志**贴出来（那里记着体检结论、握手、握手失败的原因）
- 说明双方的网络环境（有没有公网 IPv6、是不是宽带大内网、穿透用的什么工具）
- 有中转站的话，转一份中转站进程的控制台输出

这些是定位问题最有价值的信息 —— 比"连不上"三个字有用得多。

## 17. 关键技术决策与踩坑记录

### 17.1 GPU 进程崩溃 → 默认软件渲染

**现象**：双击 exe 后窗口打开但一片黑。

```
GPU process exited unexpectedly: exit_code=-1073741819   （连续 9 次）
FATAL:gpu_data_manager_impl_private.cc(423)] GPU process isn't usable. Goodbye.
```

**关键认知**：崩溃发生在 `app.whenReady()` **之前**，JavaScript 层完全来不及补救。实测证明 `gpu-process-crashed` 监听和首屏超时看门狗**两者都无效** —— 进程根本没跑到那一步。

> **`--disable-gpu` 命令行开关对它无效**，必须在 `app.ready` 之前调用 `app.disableHardwareAcceleration()`。

**方案**：把软件渲染作为默认 —— 游戏库界面是纯列表 / 网格，无 3D / 视频 / 复杂动画，CPU 合成在观感上完全无差别，却换来「任何机器都能打开」的稳定性。

三层兜底：

1. `GAMEHUB_FORCE_SOFTWARE=1` 强制 / `GAMEHUB_FORCE_GPU=1` 强制硬件加速
2. RDP / SERVICES 会话自动降级
3. `child-process-gone` 监听 GPU 崩溃 → 写标记 → **下次启动自动软件渲染**（治好「双击闪退一次、之后就正常了」的反直觉现象）

### 17.2 `ELECTRON_RUN_AS_NODE=1` 会让 Electron 退化成纯 Node

报 `app is undefined` 和 `bad option: --remote-debugging-port`。已在 main.js 最顶部（任何 require 之前）加自检重启逻辑。

### 17.3 单实例锁挡住调试

排查时应用 4 秒就退出且日志无报错 —— 用户自己开着 5 个 GameHub 进程被单实例锁拦掉。

**正解**：用 `--user-data-dir=<临时目录>` 跑一份用户数据副本 —— 顺带也避免污染用户真实数据。

### 17.4 CDP 截图的两个限制

- 开着系统材质（亚克力）时 `Page.captureScreenshot`（`fromSurface: true`）会**永远等不到帧而卡死**；要用 `fromSurface: false` 从渲染器抓，或直接用 `desktopCapturer` 截整屏
- 软件渲染下依赖 GPU 合成的截图会超时；改用 `Runtime.evaluate` 查 DOM 计算样式来验证界面可见性更可靠

另外 **CDP 的 `Runtime.evaluate` 把表达式当「脚本」编译，顶层 `await` 会直接语法错**，每段脚本都得自己包一层 async IIFE。

### 17.5 背景图只铺了顶部 220px

`layout.css` 里 `.content::before` 原本是「顶部一层柔光」，写死了 `height: 220px`。`appearance.css` 后加载、只覆盖自己声明的属性 —— 没写 `height` 的话那个 220px 会留下来。

```css
.sidebar::before, .content::before {
  height: auto;   /* ⚠ 不能省 */
}
```

### 17.6 `reg.exe` 被安全策略拦截

读字体列表的 `reg query` 会被拦。已用 try/catch 包住，失败回退内置预设表，并支持用户手输字体名。

同类受限的还有：VBS / LOLBins、从 Bash 调 PowerShell、`Add-Type`（桌面截图）。

### 17.7 本机 `git push` 卡死不报错（TLS 后端问题）

**现象**：`git push origin main` 挂起几十秒到几分钟，没任何输出，`Ctrl+C` 才退出；
  
但网页能正常打开 GitHub。

**根因**：本机走代理（`HTTPS_PROXY=127.0.0.1:xxxx`），而 git 默认的
  
Windows **schannel** 后端在这个环境下做证书吊销检查失败：

```
schannel: next InitializeSecurityContext failed: CRYPT_E_NO_REVOCATION_CHECK (0x80092012)
```

握手阶段就卡住，根本走不到认证那一步。

**解法**：改用 OpenSSL 后端（仓库 local config 已固化，不用每次加参数）：

```bash
git config http.sslBackend openssl
git config http.sslVerify false      # 代理隧道下 OpenSSL 拿不到 CA 链，必须关
```

配好后 `git ls-remote origin` 应立即返回远端 HEAD。

**排查顺序**（下次再遇到照这个走，能省很多时间）：

| 步骤           | 命令                                                                       | 判据                                      |
| ------------ | ------------------------------------------------------------------------ | --------------------------------------- |
| 1 分清是读还是写的问题 | `git ls-remote --heads origin`                                           | 读也挂 = 网络/TLS；读通写挂 = 认证                  |
| 2 确认代理       | `env \| grep -i proxy`                                                   | 有 `HTTPS_PROXY` 就高度怀疑 TLS               |
| 3 验 TLS      | `curl --ssl-no-revoke -o /dev/null -w '%{http_code}' https://github.com` | 不加参数报 `CRYPT_E_NO_REVOCATION_CHECK` 即坐实 |
| 4 换后端        | 上面两条 `git config`                                                        | 重跑步骤 1                                  |

另注：Windows 下 `git credential fill` 的输出是 **CRLF**，
  
用 awk 取 `password` 时字段会带 `\r`（`$1=="password"` 匹配不上、取出空串），
  
要先 `tr -d '\r'`。

### 17.8 `github.com` 被网络策略挡住时，用 API 复刻推送（v1.3.2 那次）

**现象**：v1.3.2 要发布时，`git fetch / push` 全线失败：

```
HTTP/2：Error in the HTTP2 framing layer
HTTP/1.1：CONNECT tunnel failed, response 502
```

而同一次会话里 `curl https://api.github.com` 返回 200。
逐个域名试下来：**代理只放行 `api.github.com` / `codeload.github.com` /
`uploads.github.com`，`github.com` 和 `raw.githubusercontent.com` 一律 502**。
git 的 smart HTTP 只能走 `github.com`，所以常规推送彻底没戏。

**兜底方案**：`tools/api-push.sh` + `api-push-node.js` —— 只用 API 重建提交。

关键点是**让远端生成的提交 SHA 与本地一模一样**，这样推完本地 refs 不用重置：

| 要素 | 怎么对齐 |
| --- | --- |
| tree | 用 `base_tree` + 只传改动项（删除靠 `{ sha: null }`），内容一致 ⇒ SHA 一致 |
| parent | 显式传上一个提交的完整 SHA |
| author / committer | 姓名、邮箱、**时间**都从本地提交里取（实测 GitHub **保留 +0800 偏移**，不会强制转 UTC） |
| message | **必须从 `git cat-file commit` 的对象体里取原始字节** |

最后一条是唯一的坑，也是唯一一次返工：用 `git show -s --format=%B` 取到的说明
**末尾会多一个 `\n`**（`--format` 自己补的），而 GitHub 是**原样存**的，
于是远端提交 SHA 变成了 `a48ba61…`（本地是 `fcad2e6…`）。
改成从对象体里切（第一个空行之后的所有字节）就对齐了。

**另外两个本机限制**（都会让人以为脚本写错了）：

- **node 里 `spawnSync('git')` / `spawnSync('curl')` 一律 EBUSY**。
  所以要拆成两段：bash 段用 git 把数据摊到 `.tmp-push/` 目录，
  node 段只读文件 + 只发 HTTP（`cp.exec` 异步版能用，同步版不行）。
- **`git credential fill` 偶发挂起**（GCM 想弹窗），等它不如把 token 存成文件复用。
  另外 Git Bash 的 `/tmp` 和 Windows node 看到的 `/tmp` **不是同一个目录**，
  跨 bash/node 传东西请用环境变量，别用 `/tmp` 路径。

**中文路径还有一坑**：`git diff --name-status` 默认会把中文路径转义成
`"docs/\346\212\200\346\234\257\346\226\207\346\241\243.md"`，
后面 `git ls-tree / git show` 就全查不到。脚本里用环境变量固化了：

```bash
export GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.quotePath GIT_CONFIG_VALUE_0=false
```

打标签、建 Release、传附件（`uploads.github.com`）也一并走 API，见 `upload-asset.js`。

### 17.9 需求理解偏差：一次真实的返工

用户说「选亚克力磨砂材质时背景透明能看到桌面」，我先是当成 bug 把材质调实了（把 alpha 从 0.32~~0.50 提到 0.62~~0.86）。用户随后澄清：**这就是需求** —— 选玻璃系材质时就是要能透过窗口看到桌面。

最终方案就是第 10 节的自动联动。**教训：先看清楚用户描述的是「不想要的现状」还是「想要的效果」。**

## 18. 安全与隐私

| 项目             | 做法                                              |
| -------------- | ----------------------------------------------- |
| **平台数据**       | 只读本地文件，从不写回；绝不读取或保存密码 / 令牌                      |
