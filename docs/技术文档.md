## 1. 项目概览

GameHub 是一个**完全离线优先**的本地游戏库管理器，把散落在 Steam / Epic / 注册表 / 自定义目录里的游戏汇成一个统一的 Steam 风格封面墙。

### 设计原则

| 原则 | 具体体现 |
|---|---|
| **只读不写** | 读取各平台本地数据时严格只读，从不写回任何平台文件 |
| **隐私硬约束** | 绝不读取、更不保存任何平台的密码 / 令牌 / 登录凭证 |
| **离线可用** | 断网时扫描、启动、分类、统计全部正常；联网只用于封面增强 |
| **不破坏宿主** | Steam 游戏交给 Steam 卸载；删除一律走回收站，绝不永久删 |
| **数据自包含** | 所有数据（含背景图副本）存在同一数据目录，可直接搬走 |

### 技术栈

- 运行时：Electron 33.4.11（Node 22 + Chromium 130）
- 渲染层：**零框架**，原生 HTML / CSS / JavaScript
- 打包：electron-builder 25（Windows portable 单文件 exe）
- 加密：Node `crypto`（scrypt）+ Electron `safeStorage`（Windows DPAPI）

## 3. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                      主进程 (main.js)                     │
│  窗口管理 · IPC 注册 · 后台任务（体积队列 / 巡检 / 自动上锁） │
├─────────────────────────────────────────────────────────┤
│  业务模块层（纯 Node，可单测，不依赖 Electron）             │
│  store · library · scanner · classify · cover · launcher  │
│  platforms · epicauth · mods · stats · uninstall          │
│  appinfo · vdfbin · imgmeta                              │
├─────────────────────────────────────────────────────────┤
│              preload.js（contextBridge 白名单）            │
├─────────────────────────────────────────────────────────┤
│                       渲染进程                            │
│  api.js → state.js → app.js → cards/detail/modals/...    │
│  background.js（外观） · css/（主题与材质）                │
└─────────────────────────────────────────────────────────┘
```

**分层约束：**
- 渲染进程拿不到任何 Node 能力，只能通过 `preload.js` 白名单里的通道
- 业务模块（`scanner` / `classify` / `stats` 等）刻意写成不依赖 Electron 的纯模块，可被 Node 直接单测
- 主进程是**状态权威**：例如「透出桌面」的最终值由主进程换算后推送给渲染层，页面不自己猜

## 5. 主进程模块详解

### 5.1 store.js —— 数据持久化

- 文件：`%APPDATA%\GameHub\library.json`，封面缓存 `covers/`，背景图 `bg/`
- **原子写入**：先写 `.tmp` 再 `rename`，避免断电 / 崩溃写坏存档
- **延迟写盘**：`saveSoon(800ms)` 把高频操作（如更新游玩时长）合并成一次 IO
- **向前兼容**：读档时 `deepMerge(默认值, 读到的数据)`，新增字段自动补到老数据上
- **损坏保护**：JSON 解析失败时先备份成 `library.json.bak` 再用默认值重建

### 5.2 scanner.js —— 游戏嗅探

四条嗅探路径：

| 方法 | 覆盖范围 | 特点 |
|---|---|---|
| `scanRegistry()` | 注册表卸载项 | 覆盖 90% 已安装游戏，带安装日期 |
| `scanSteam()` | Steam 库 | 解析 `libraryfolders.vdf` + `appmanifest_*.acf` |
| `scanEpic()` | Epic 清单 | 解析 `ProgramData` 下的 `.item` JSON |
| `scanFolder()` | 用户指定目录 | 递归 + 启发式识别 |

**误报控制**是这里最难的部分：
- **exe 名归一化**：`PotPlayer64.exe` 的 base 是 `potplayer64`，与黑名单 `potplayer` 精确匹配不上。必须先剥掉 `_util` / `_x64` / 数字 / 版本号后缀再比对（同类漏网的还有 `cloudmusic_util`、`TIM3.0`）
- **平台客户端根识别**：不能只看 `steam.exe` 存在（Mod 目录也带），要看「主程序 + 辅助进程同时存在」或强特征文件名
- **分级清理**：手动添加 / 玩过 / 收藏 / 有备注的条目**永远不自动删**

### 5.3 classify.js —— 分类与识别

- `classify(name)`：**25 个分类**，加权关键词匹配，中英文双语词表
- `scoreRegistryEntry()`：给一条注册表卸载项打分，判断「它像不像游戏」
- `pickMainExe()`：从一个目录里挑出最像「游戏主程序」的 exe

用户手动改过的分类会被**锁定**，不被自动归类覆盖。

### 5.4 cover.js —— 封面管理

四种来源，优先级由用户自选：

1. **从 exe 提取图标**（默认，离线可用，square 图标居中贴到渐变底上）
2. **用户手动指定图片**（拖拽 / 文件选择）
3. **联网搜索**：按名字去 Steam 查 AppID，再抓官方封面（搜不到就跳过，不打扰用户）
4. **主题色首字母占位**

`coverKind` 取值：`none` | `icon` | `custom` | `steam`。用户自己设的（`custom`）永远不被自动覆盖。

### 5.5 launcher.js —— 启动与进程守护

- 直接跑 exe / 走 `steam://run/<appid>` 协议 / 走自定义启动参数
- **进程守护计时**：游戏开着时每秒计时，关掉后把时长写回游戏库
- 启动失败给出人话错误（文件不存在 / 权限不足 / 需要管理员）

### 5.6 platforms.js —— 平台数据抓取

**隐私硬约束（改代码时不要破坏）：**
1. 本模块**只读**本地文件，从不写回任何平台的文件
2. 绝不读取、更不会保存任何密码 / 令牌 / 登录凭证
3. 只使用平台客户端已经落在本地的那份数据

### 5.7 epicauth.js —— Epic 登录

让用户在 GameHub 里登录 Epic，读到两样东西：
- 拥有的游戏全清单（**含领了但没下载的** —— 本地清单读不到这些）
- 官方封面图（CDN 直链）

**边界与事实**：Epic **没有**开放面向第三方的玩家数据 API（官方论坛已明确回复）。所以：
- ✅ 能拿到：账号信息、已购游戏清单、官方封面
- ❌ 拿不到：玩家累计游玩时长、成就进度

登录 token 存在 `userData/epic-auth.json`，用 Electron `safeStorage` 加密（Windows 上走 DPAPI，密钥绑当前用户账户）。

> **关于客户端凭据**：源码里的 `CLIENT_ID` / `CLIENT_SECRET` 是 Epic **启动器本体**的公开客户端标识（开源社区 Heroic / Legendary 等普遍这样用），不是任何人的账号密码。不需要改代码即可覆盖：
> ```bash
> GAMEHUB_EPIC_CLIENT_ID=xxx GAMEHUB_EPIC_CLIENT_SECRET=yyy npm start
> ```

### 5.8 其它模块

| 模块 | 职责 |
|---|---|
| `appinfo.js` | 解析 Steam `appinfo.vdf`，给「没安装的游戏」名字兜底（最准的来源） |
| `vdfbin.js` | Binary KeyValues 解析器，读 Steam 成就解锁位图与成就定义 |
| `imgmeta.js` | 只读文件头几十字节判断图片尺寸，应对 Steam 千奇百怪的封面文件名 |

| `uninstall.js` | 见 [第 11 节](#11-卸载游戏) |

## 7. IPC 通信与 API 分层

```
渲染层  window.API.xxx()
   ↓
api.js  （统一 try/catch + JSON 化）
   ↓
preload.js  contextBridge 白名单
   ↓
main.js  ipcMain.handle(...)
   ↓
业务模块
```

共 **60 个 IPC 通道**，按域分组：

| 域 | 通道 |
|---|---|
| 应用 / 窗口 | `app:info`、`win:*` |
| 设置 | `settings:get`、`settings:set` |
| 外观 | `appearance:urls` / `setImage` / `clearImage` / `fonts` / `desktopMaterial` / `desktopMaterialSupport` |
| 游戏库 | `library:list` / `add` / `addMany` / `update` / `remove` / `clear` |
| 游戏 | `game:launch` / `stop` / `openFolder` / `calcSize` / `uninstall` / `uninstallInfo` |
| 扫描 | `scan:auto` / `scan:folder` / `scan:cancel` / `scan:defaultFolders` |
| 封面 | `cover:*`（extract / fetchSteam / searchOne / reset / …） |
| 平台 | `platform:list` / `sync` / `action`、`epic:login` / `logout` / `status` |
| MOD | `mod:list` / `setEnabled` / `remove` / `addManual` / `openWorkshop` / `openNexus` |
| 隐藏空间 | `hidden:setup` / `unlock` / `lock` / `status` / `setHidden` / `changePassword` / `disable` |
| 统计 / 分类 / 对话框 / Shell | `stats:get`、`category:*`、`dialog:*`、`shell:*` |

### 反向推送

主进程 → 渲染层的推送只有一个：`appearance:material`（窗口材质变化）。
主进程是权威，页面订阅后更新样式，避免两边状态对不上。

## 8. 数据模型与持久化

### library.json 顶层结构

```jsonc
{
  "version": 2,
  "games":    [ /* Game 对象数组 */ ],
  "sessions": [ /* 游玩流水 */ ],
  "settings": { /* 见下 */ }
}
```

### Game 对象主要字段

```js
{
  id, name, exePath, installDir, source,       // 来源：steam / epic / manual / …
  publisher, version, categories: [], altNames: [],
  installDate, sizeBytes, sizeComputedAt,
  favorite: false, hidden: false,
  clearState: 'cleared' | 'multi' | 'uncleared',  // 默认 'uncleared'
  playCount, totalPlayMs, lastPlayedAt,
  playtimeFromSteam: false, steamSyncedAt,     // 时长是否已与 Steam 对过
  coverPath, coverKind, steamAppId, launchArgs, note,
  missing: false, addedAt, updatedAt
}
```

> **不存在「未标记」这一档通关状态**：所有添加的游戏默认未通关，老数据里读到空串一律归到 `uncleared`。

### 设置项（关键部分）

```js
{
  theme: 'dark', sortBy: 'added', viewMode: 'grid', cardSize: 'medium',
  fontFamily: '', fontSize: 13.5,     // 界面字体
  desktopMaterial: 'auto',            // 透出桌面：auto | off | acrylic | mica | tabbed
  bg: {
    sidebar: { type, image, fit, opacity, blur, dim, material, tint },
    content: { /* 同构，两栏独立 */ }
  },
  hidden: { enabled, salt, hash, hint, autoLockMinutes },
  windowBounds: null
}
```

## 9. 外观自定义系统

### 9.1 为什么背景画在伪元素上

背景**不画在元素自己的 `background` 上**，而是画在 `::before`（图片层）和 `::after`（压暗遮罩）两个伪元素上。

好处：内容层的层级、图标的点击区域完全不受影响，也不会出现「改了背景色，结果按钮 hover 底变色」这类连锁反应。

### 9.2 层叠：沉背景而不是抬内容

```css
.sidebar, .content { position: relative; isolation: isolate; }
.sidebar::before, .content::before,
.sidebar::after,  .content::after { z-index: -1; }
```

> ⚠️ **血的教训**：最初写的是 `.content > * { z-index: 1 }`（抬内容），结果顶栏的「⋮ 更多选项」下拉菜单被下面 DOM 靠后的卡片区盖住了。
>
> **「抬内容」和「沉背景」效果看似一样，但抬内容会改变层叠上下文，把原本能浮起来的东西（下拉、tooltip）一起压住。**
>
> `isolation: isolate` 把负 z-index 关在本容器内，伪元素落在「容器背景之上、内容之下」，正好是想要的层次。

### 9.3 四种材质

| 材质 | 不透明度（常规） | 不透明度（透视版） | 观感 |
|---|---|---|---|
| 磨砂玻璃 `frosted` | 0.86 | 0.30 | 强模糊 + 轻微降饱和，隔一层毛玻璃 |
| 亚克力 `acrylic` | 0.78 | 0.22 | 中等模糊 + 提饱和提亮，接近 Win11 亚克力 |
| 玻璃 `glass` | 0.66 | 0.16 | 轻模糊 + 明显厚度与高光边 |
| 液态玻璃 `liquid` | 0.62 | 0.13 | 有体积感，见下 |

**共同约束：必须有实体感。** 纯半透明叠深色底会看起来像个「透明窟窿」，所以每种材质都给了：一层底色 + 一层纵向高光 + 内嵌高光边。

**液态玻璃**的「体积感」靠四层光叠出来：
- 顶部一条 2px 的窄亮边（玻璃边缘折射高光 —— 这是「液态」最关键的一笔）
- 左上角柔和的镜面高光
- 右下角冷色反射 + 左下角暖色微光（制造液体的色温差）
- 底部内阴影压出厚度 + 外投影让它从背景上浮起来

```css
backdrop-filter: blur(27px) saturate(205%) brightness(1.16) contrast(1.03);
```

### 9.4 氛围光

`backdrop-filter` 需要有「背后有东西」才看得出来。启用材质时给 `.app` 加 `.has-material` 铺一层氛围渐变光（左上偏蓝、右下偏青、中间一点紫）。

alpha 要够浓（0.46 / 0.38 / 0.26）—— 第一版用 0.22 完全看不出效果。

同步逻辑用 `syncAmbientFromDom()`：**直接看 DOM 上挂着哪个类**，而不是读设置对象 —— 因为设置面板改材质走的是 `applySlot`（实时预览），读设置会漏。

### 9.5 字体与字号

- 字体列表：`reg query` 读注册表拿全量，失败回退**内置 60+ 精选预设**
  > 实测部分环境 `reg.exe` 被安全策略黑名单拦掉 —— 所以预设表必须够全，并支持用户**手输字体名**，两条路都要有
- 字号全局生效：`tools/rewrite-font-size.py` 把 CSS 里 **182 处**正文级字号（10~15px）批量改成 `calc(var(--fs-base) * 系数)`，系数 = 原值 / 13.5，所以默认值下渲染结果与改动前完全一致（实测 `.si-label` 13.0005px vs 原 13px）。18px+ 的大标题保持固定，避免撑坏版式。

## 10. 透出桌面（窗口材质）

### 10.1 核心事实

> **CSS `backdrop-filter` 只能采样「页面内」已画出的内容，永远看不到桌面。**

无论把材质层调得多透，底下也只有深色的页面底色。想让窗口真的透出桌面，只能让 Windows 的 DWM 去合成 —— 也就是主进程的 `win.setBackgroundMaterial()`。

### 10.2 实现：材质 ↔ 透出桌面 自动联动

`desktopMaterial` 取值：`auto`（默认）/ `off` / `acrylic` / `mica` / `tabbed`

```
auto → 左右任一栏用了玻璃系材质（frosted/acrylic/glass/liquid）
       → 窗口自动开 acrylic
       → 换回图片或纯色底 → 自动收回
```

- **主进程是权威**：`resolveDesktopMaterial()` 换算后经 `appearance:material` 推送给渲染层；渲染层首屏用同一套规则镜像计算，之后以推送为准
- 旧数据里的 `'none'` 兼容为 `auto`（否则老用户开了玻璃材质也透不出桌面）
- 系统要求：Windows 11（build ≥ 22000），其它系统静默忽略

### 10.3 透视版材质变量

开了透出桌面后，CSS 把 `--mat-*` 换成 `--mat-*-see`：

```css
html[data-desktop-material] {
  --mat-frosted: var(--mat-frosted-see);
  --mat-acrylic: var(--mat-acrylic-see);
  --mat-glass:   var(--mat-glass-see);
  --mat-liquid:  var(--mat-liquid-see);
}
```

**只降底色不降高光** —— 折射高光 / 镜面光 / 内嵌边是「玻璃感」的来源，留着它们，面板放透之后依然像一块玻璃，而不是一块空缺。

液态玻璃放透后去掉外投影（黑影会糊在桌面上），内嵌高光与底部内阴影保留。

## 11. 卸载游戏

三类游戏的卸载方式完全不同，`src/main/uninstall.js` 分开处理：

| 类型 | 方式 | 理由 |
|---|---|---|
| **Steam** | `steam://uninstall/<appid>` | Steam 有自己的库状态、清单、云存档。我们直接删目录会让它变成「文件缺失」坏状态 |
| **Epic** | `com.epicgames.launcher://apps/<AppName>?action=uninstall` | ⚠ AppName **没有存在游戏对象里**（扫描时只用它算了 id），卸载时要现去 `.item` 清单按 `InstallLocation` 反查 |
| **本地 / 手动** | 先找自带卸载器（`unins000.exe` 等，目录 + 注册表两路查），找不到就把整个目录 `shell.trashItem` | 一律走回收站，不是永久删 |

### 安全红线（写死在代码里）

- **禁删系统目录**：盘符根 / Windows / Program Files 根 / 用户目录根
- **删除一律走回收站**
- 每次卸载前把「要删什么」报清楚

### 库记录何时清

只有 `remove`（用户就是要清）和 `trash`（文件已进回收站）才顺手删记录；
`platform` 和跑卸载向导的情况**先留着** —— 那些流程还没走完，删了记录用户就找不回条目了。

## 13. 内置浏览器与 MOD 下载

### 13.1 这个功能要解决什么

在 MOD 这件事上，最容易踩的坑不是下载不下来，而是**放错目录** ——
而且放错**不会报错，只会静默失效**：进游戏一看，MOD 没生效，日志里什么都没有。

原本「N 网找 MOD」是丢给系统浏览器的：文件落到「下载」目录，
用户得自己找文件、自己解压、自己判断该放哪个游戏的哪个子目录。
内置浏览器把这个链路整个接过来：在软件内打开 N 网 → 下载被接管 →
按规则直接落到这款游戏的 MOD 目录 → 按需自动解压。

顺带一个附加好处：N 网给免费用户的「断点续传」在 Chromium 内核下支持最好，
而 Electron 就是 Chromium。

### 13.2 模块构成

| 文件 | 职责 |
|---|---|
| `src/main/browser.js` | `BrowserService`：窗口生命周期 + 下载接管 + 事件出口 |
| `src/main/modpaths.js` | MOD 目录规则引擎（纯 Node，可单测） |
| `src/main/unzip.js` | 纯 Node ZIP 解压（含 Zip Slip 防护） |
| `src/renderer/browser.html` | 浏览器窗口的壳：自绘工具条 + `<webview>` |
| `src/renderer/js/browser.js` | 工具条交互与状态显示，**不做业务判断** |
| `preload-browser.js` | 浏览器窗口专用 preload，能力面刻意做窄 |

### 13.3 MOD 目录规则引擎（联网查证后的结论）

规则优先级：**手动指定 > Steam AppID 精确匹配 > 名称关键词 > 目录探测兜底**。
另外只要磁盘上真有符合常见命名的目录，就以它为准 ——
实测目录比规则推断可靠。

一部分规则是**反直觉**的，也是这套引擎存在的意义：

| 游戏 | MOD 目录 | 容易搞错的点 |
|---|---|---|
| 老滚 5 / 辐射 4 / 湮灭 | `Data` | **不是** `Mods` |
| 巫师 3 | `mods/mod<名字>` | 文件夹名**必须以 `mod` 开头** |
| 赛博朋克 2077 | `archive/pc/mod` | |
| 艾尔登法环 | `Game/mod` | |
| 黑神话悟空 | `b1/Content/Paks/~mods` | |
| 幻兽帕鲁 | `Pal/Content/Paks/~mods` | |
| 怪物猎人 | `nativePC` | |
| 博德之门 3 | `%LOCALAPPDATA%\Larian Studios\Baldur's Gate 3\Mods` | **不在游戏目录里** |
| 我的世界 | `%APPDATA%\.minecraft\mods` | 同上 |
| 骑马与砍杀 2 | `Modules` | 不是 `Mods` |
| 无人深空 | `GAMEDATA/PCBANKS/MODS` | |
| 英灵神殿 | `BepInEx/plugins` | |
| 城市天际线 | `Files/Mods` | |
| 欧洲卡车 2 | `mod`（**单数**） | 在「文档」下 |
| 农场模拟 / 僵尸毁灭工程 / 饥荒 | 「文档」或用户目录 | |

**认不出来时不硬猜**：退化成弹窗让用户选一次。
理由就是开头那句 —— 放错不报错，比让用户多点一下糟得多。

### 13.4 下载落点决策（`main.js` 的 `decideModDownloadDir`）

三种模式（设置里选）：

| 模式 | 行为 |
|---|---|
| 自动进游戏 MOD 目录（默认） | 按 13.3 的规则推断 |
| 固定文件夹 | 一律落到设置里指定的目录 |
| 每次问我 | 弹保存对话框，默认位置填推断结果 |

界面预览（`mod:downloadTarget`）和下载回调**共用同一份函数**，
避免"界面显示 A、实际存到 B"这种最难查的不一致。

### 13.5 预留的扩展接口

需求明确要求「预留接口方便后续修改及添加功能」，
所以浏览器服务刻意把「开窗口」和「用浏览器」分开，上层只依赖这几个口子：

| 接口 | 用途 | 以后能怎么长 |
|---|---|---|
| `open(url, { title, context })` | 开窗口，`context` 会原样带回给回调 | 加「在新标签打开」只需自己管 handle |
| `sendTo(id, channel, payload)` | 主进程主动推消息给浏览器界面 | 加通知 / 工具栏状态 / 注入脚本都走这里，不用开新 IPC |
| `onReady(id, rec)` | 页面就绪回调 | 初始化数据必须在这时推，早了会丢 |
| `onDownload(info)` | 问上层「存哪」，支持返回 Promise | 换落点策略只改这一个回调 |
| `onEvent(ev)` | 统一事件出口 | 以后做「下载中心」直接接这里 |
| `navigate / close / list / downloadList / cancelDownload` | 基本控制 | |

想改成「内嵌到主界面的标签页」形态，
只需把 `_createWindow` 里的 `BrowserWindow` 换成 `WebContentsView`，
上面这套接口一行都不用动。

### 13.6 安全边界

浏览器窗口里跑的是**外部不可信站点**，所以：

- `nodeIntegration: false` + `contextIsolation: true`
- 用**独立的 `preload-browser.js`**，不是主界面那个（后者暴露了几十个通道）
- 独立 session 分区 `persist:gamehub-browser`，不污染主界面登录态
- 只放行 `http(s)`；`nxm://` 之类协议交给系统处理
- 网页想开新窗口一律拒绝，收敛成同窗口跳转
- 解压有 Zip Slip 防护（拒绝绝对路径、`..` 越界）

### 13.7 踩过的坑（本功能专属）

- **`<webview>` 不写 `partition` 就整个失效**
  不指定分区时 webview 跑在默认 session 上，
  主进程挂在 `persist:gamehub-browser` 上的 `will-download` **永远收不到**，
  表现是"下载了但没接管"。这是本轮最隐蔽的一个坑。
- **`webviewTag` 默认不开**，壳页面里的 `<webview>` 必须显式启用。
- **下载来自 guest webContents**，不等于宿主窗口的 `webContents`，
  直接 `===` 比对全部失配、进度条不动。要在 `did-attach-webview` 时登记 guest。
- **`setSavePath` 必须给完整文件路径**，只给目录会静默走默认下载路径。
- **`loadFile` 是 `BrowserWindow` 的方法**，不是 `webContents` 的。
- **上层没配 `onDownload` 时不能顺手取消下载** —— 无声无息消失比存错地方更难查。
- **打包清单要带上 `preload-browser.js`**，否则打出的 exe 里浏览器窗口没有 preload。
- 本机调试若 GPU 进程 FATAL，加 `--no-sandbox` 可绕过（沙箱拉不起 GPU 进程）。

## 16. 关键技术决策与踩坑记录

### 16.1 GPU 进程崩溃 → 默认软件渲染

**现象**：双击 exe 后窗口打开但一片黑。

```
GPU process exited unexpectedly: exit_code=-1073741819   （连续 9 次）
FATAL:gpu_data_manager_impl_private.cc(423)] GPU process isn't usable. Goodbye.
```

**关键认知**：崩溃发生在 `app.whenReady()` **之前**，JavaScript 层完全来不及补救。实测证明 `gpu-process-crashed` 监听和首屏超时看门狗**两者都无效** —— 进程根本没跑到那一步。

> **`--disable-gpu` 命令行开关对它无效**，必须在 `app.ready` 之前调用 `app.disableHardwareAcceleration()`。

**方案**：把软件渲染作为默认 —— 游戏库界面是纯列表 / 网格，无 3D / 视频 / 复杂动画，CPU 合成在观感上完全无差别，却换来「任何机器都能打开」的稳定性。

三层兜底：
1. `GAMEHUB_FORCE_SOFTWARE=1` 强制 / `GAMEHUB_FORCE_GPU=1` 强制硬件加速
2. RDP / SERVICES 会话自动降级
3. `child-process-gone` 监听 GPU 崩溃 → 写标记 → **下次启动自动软件渲染**（治好「双击闪退一次、之后就正常了」的反直觉现象）

### 16.2 `ELECTRON_RUN_AS_NODE=1` 会让 Electron 退化成纯 Node

报 `app is undefined` 和 `bad option: --remote-debugging-port`。已在 main.js 最顶部（任何 require 之前）加自检重启逻辑。

### 16.3 单实例锁挡住调试

排查时应用 4 秒就退出且日志无报错 —— 用户自己开着 5 个 GameHub 进程被单实例锁拦掉。

**正解**：用 `--user-data-dir=<临时目录>` 跑一份用户数据副本 —— 顺带也避免污染用户真实数据。

### 16.4 CDP 截图的两个限制

- 开着系统材质（亚克力）时 `Page.captureScreenshot`（`fromSurface: true`）会**永远等不到帧而卡死**；要用 `fromSurface: false` 从渲染器抓，或直接用 `desktopCapturer` 截整屏
- 软件渲染下依赖 GPU 合成的截图会超时；改用 `Runtime.evaluate` 查 DOM 计算样式来验证界面可见性更可靠

另外 **CDP 的 `Runtime.evaluate` 把表达式当「脚本」编译，顶层 `await` 会直接语法错**，每段脚本都得自己包一层 async IIFE。

### 16.5 背景图只铺了顶部 220px

`layout.css` 里 `.content::before` 原本是「顶部一层柔光」，写死了 `height: 220px`。`appearance.css` 后加载、只覆盖自己声明的属性 —— 没写 `height` 的话那个 220px 会留下来。

```css
.sidebar::before, .content::before {
  height: auto;   /* ⚠ 不能省 */
}
```

### 16.6 `reg.exe` 被安全策略拦截

读字体列表的 `reg query` 会被拦。已用 try/catch 包住，失败回退内置预设表，并支持用户手输字体名。

同类受限的还有：VBS / LOLBins、从 Bash 调 PowerShell、`Add-Type`（桌面截图）。

### 16.7 需求理解偏差：一次真实的返工

用户说「选亚克力磨砂材质时背景透明能看到桌面」，我先是当成 bug 把材质调实了（把 alpha 从 0.32~0.50 提到 0.62~0.86）。用户随后澄清：**这就是需求** —— 选玻璃系材质时就是要能透过窗口看到桌面。

最终方案就是第 10 节的自动联动。**教训：先看清楚用户描述的是「不想要的现状」还是「想要的效果」。**

## 17. 安全与隐私

| 项目 | 做法 |
|---|---|
| **平台数据** | 只读本地文件，从不写回；绝不读取或保存密码 / 令牌 |
| **隐藏空间** | scrypt + 随机盐单向哈希，明文不落盘；未解锁时服务端即过滤 |
| **Epic token** | `safeStorage` 加密（Windows DPAPI，密钥绑当前用户账户），仓库里没有 |
| **删除操作** | 禁删系统目录；一律走回收站，绝不永久删 |
| **删库记录** | 平台卸载 / 跑卸载向导时先保留记录，流程走完才清 |
| **联网** | 仅用于封面增强与 Epic 登录；断网时全部核心功能正常 |
